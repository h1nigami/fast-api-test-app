# Event Booking API

Тестовое задание: реализовать API для бронирования мест на мероприятие.
Ограничение: один пользователь не может забронировать одно и то же событие дважды.

Цель решения — показать понимание архитектуры backend-приложений,
работы с БД и бизнес-логики, а не просто реализовать CRUD.

---

## Почему FastAPI

FastAPI был выбран как инструмент для быстрой и явной разработки API.

Причины выбора:

- строгая типизация входных и выходных данных через Pydantic
- автоматическая валидация запросов
- понятное разделение HTTP-слоя и бизнес-логики
- встроенная документация (Swagger) для проверки и демонстрации API

FastAPI позволяет сфокусироваться на логике и структуре приложения,
что особенно важно в рамках тестового задания.

---

## Почему SQLite

SQLite используется по практическим причинам:

- не требует отдельного сервера БД
- позволяет запустить проект сразу после клонирования
- минимизирует инфраструктурную сложность

Важно отметить, что архитектура приложения **не привязана к SQLite**.
База данных может быть заменена на PostgreSQL или другую СУБД
без изменений бизнес-логики.

---

## Почему SQLAlchemy

SQLAlchemy в проекте используется **исключительно как инструмент для ускорения разработки**.

Это осознанный компромисс:

- ORM позволяет быстро описать модели
- уменьшает количество шаблонного SQL-кода
- упрощает работу в рамках тестового задания

При этом важно понимать, что:

- ORM не скрывает знание SQL
- вся бизнес-логика построена вокруг явных запросов
- ограничения целостности задаются на уровне базы данных

В реальных высоконагруженных системах
или при сложной доменной логике
я предпочитаю использовать SQL напрямую
или минимальный слой абстракции поверх него.

## Архитектура проекта

Проект разделён на логические слои:

app/
├── main.py # точка входа
├── api/ # HTTP-роутеры
├── schemas/ # Pydantic схемы
├── models/ # SQLAlchemy модели
├── repositories/ # работа с БД
├── services/ # бизнес-логика
├── core/ # инфраструктура (БД)


Такое разделение позволяет:
- изолировать бизнес-логику
- упростить тестирование
- избежать смешивания HTTP и логики работы с данными

## Модель данных

### events
- id
- name
- total_seats — вместимость события

### bookings
- id
- event_id
- user_id
- created_at

Дополнительно:
- уникальное ограничение `(event_id, user_id)`
  для защиты от повторного бронирования

---

## Как работает бронирование

Endpoint:
POST /api/bookings/reserve

Пример запроса:

```json
{
  "event_id": 1,
  "user_id": "user123"
}

Логика:

Запрос валидируется Pydantic-схемой

Проверяется существование события

Проверяется, не бронировал ли пользователь ранее

Проверяется наличие свободных мест

Создаётся запись о бронировании

Свободные места

Поле total_seats не изменяется при бронировании.

Это осознанное решение:

total_seats описывает вместимость

занятые места определяются количеством записей в bookings

свободные места считаются динамически
free_seats = total_seats - count(bookings)


Конкурентность и целостность данных

Для защиты от конкурентных сценариев используются:

транзакции на уровне сессии БД

уникальное ограничение (event_id, user_id)

обработка ошибок целостности

Даже при одновременных запросах
пользователь не сможет забронировать событие дважды.

Для SQLite это практичный и достаточный подход.
При использовании PostgreSQL возможно усиление
через SELECT ... FOR UPDATE.
```
